核心目标：
1. 接入当前第三方中转服务商 NayutoAI，并为后续更多中转服务商保留轻量扩展边界。
2. 不改变现有 TokenMeter 面板布局、交互方式和使用习惯。
3. 中转“今日分时”必须直接复用当前小米或 DeepSeek 的分时图表与分钟详情组件，不做第三方网站控制台。
4. 分钟详情保持现有结构：时间、总计、输入（命中缓存）、输入（未命中缓存）、输出、缓存命中率、本分钟消耗金额。
5. 悬浮球完全复用小米现有金额球样式和交互，只替换中转的今日使用金额、余额和美元符号；不要增加进度环、百分比或中转专属样式。
6. 中转分时逻辑独立于小米和 DeepSeek。主数据源优先使用：
   GET https://nayutoai.xyz/portal/user/usage?page=1&page_size=50
7. 中转分钟金额应汇总服务商返回的实际消费金额，不套用小米或 DeepSeek 的价格公式。
8. 登录体验与小米一致：程序打开隔离浏览器，用户登录后自动获取凭证。但中转应根据真实请求捕获 Authorization Bearer；是否还需 Cookie/CSRF必须从附件和真实请求确认。
9. 凭证必须使用项目现有安全存储方案，不得写入源码、普通配置或日志。
10. 不得影响小米、DeepSeek的登录、轮询、缓存、分时、切换和悬浮球。

必须遵守以下实施流程：

A. 开始前
- 完整阅读项目 AGENTS.md 和上述需求文档。
- 执行 git status，保护所有已有、未提交和未跟踪文件，不覆盖用户改动。
- 阅读“中转请求和响应参数.txt”，不要复述或输出其中的 Bearer Token、Cookie等秘密。
- 搜索并画出当前真实调用链：服务商注册/配置 → 登录与凭证保存 → FetchTask/网络请求 → 响应解析 → 缓存/分钟聚合 → ViewModel/UI → 悬浮球。
- 找出小米和 DeepSeek 的对应实现并比较差异，特别检查已有 provider 抽象、browser_cookie/浏览器捕获、Credential Manager、后台轮询、迟到结果保护和 minute_usage。
- 搜索已有测试和真实样例，先复用，再新增。
- 在完成上述检查前不要开始编码，也不要猜字段、接口、类名或存储结构。

B. 设计约束
- 优先扩展现有 provider/adapter/fetcher 结构；如果没有抽象，只增加完成当前需求所需的最小适配边界，不做大规模架构重构。
- 服务商差异放在适配层：URL、认证、分页、字段解析、Token口径、币种和能力。
- UI只消费统一后的展示模型，不直接解析第三方JSON或拼认证头。
- 当前显示服务商与后台采集服务商保持隔离：每个结果写入所属服务商缓存，只有仍为当前服务商时才更新可见UI。
- 保留项目现有请求防重入、在途标记、迟到结果保护和后台定时采集。
- 分页必须有终止条件和最大保护；按Request ID优先去重，重复刷新不得重复累计。
- 金额使用十进制类型累计。
- 必须确认 input_tokens 是否包含缓存Token：若响应已经把非缓存输入与cache_read分开，直接映射；只有确认缓存是输入子集时才能相减。用附件真实样例固定此口径。
- 分钟缓存命中率 = 命中缓存输入 / (命中缓存输入 + 未命中缓存输入)，处理分母为0。
- 网络失败保留最后成功缓存；401/403提示重新连接；中转失败不能阻塞其他服务商。

C. UI要求
- 只在现有服务商选择中增加中转项。
- 保持主面板所有区域、控件位置、主题、日期切换、刷新和统计布局不变。
- 复用现有“今日分时”图表、图例、滚动条和Tooltip。
- 中转Tooltip顺序必须与小米/DeepSeek一致：
  时间 / 总计
  输入（命中缓存）
  输入（未命中缓存）
  输出
  缓存命中率
  本分钟消耗金额
- 中转金额显示美元符号 `$`；分钟金额需要保留小额账单所需精度。
- 悬浮球不要新建视觉样式，直接走小米现有金额球组件。

D. 验证要求
- 为附件真实响应添加解析测试。
- 覆盖分页、去重、重复轮询、时间归桶、跨日、Token合计、缓存命中率、实际金额精度、空响应、核心字段异常、401/403/429/5xx/超时。
- 覆盖多服务商切换和迟到结果，证明不会串数据。
- 运行现有完整测试，并单独回归小米、DeepSeek。
- 如果环境允许，运行程序做实际UI验证，逐项对照现有小米/DeepSeek分时和悬浮球。
- 不要把静态检查描述成运行时验证；任何未执行的测试、真实登录、真实API或UI验证都要明确列出。
