# TokenMeter 多服务商后台持续采集与分时连续性优化需求文档

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档状态 | 待评审 |
| 编写日期 | 2026-08-13 |
| 需求类型 | 功能优化、Bug 修复 |
| 适用项目 | TokenMeter（TokenSpider） |
| 涉及服务商 | DeepSeek、小米 MiMo、Codex，以及后续新增 Provider |

## 2. 背景与问题

TokenMeter 当前在标题栏提供服务商下拉框，但“当前展示的服务商”和“后台采集的服务商”使用同一个 `ACTIVE_PROVIDER` 配置。

现有链路如下：

1. 标题栏切换服务商后写入 `ACTIVE_PROVIDER`。
2. 定时刷新仅根据 `ACTIVE_PROVIDER` 创建一个采集任务。
3. `active_providers()` 只返回当前选中的单个 Provider。
4. `TokenData.fetch()` 只采集该 Provider，并更新该 Provider 的本地快照。
5. 未被选中的服务商即使已经配置有效凭据，也不会继续采样。

因此，当用户长时间查看 Codex 后再切回小米 MiMo，MiMo 可能只保留两次相距很远的累计快照。例如：

```text
14:28  MiMo 最后一次成功采样：累计值 A
14:29～17:00  用户查看 Codex，MiMo 未采样
17:01  切回 MiMo并成功采样：累计值 B
```

现有分时算法会按照既定口径，把 `B - A` 平均写入 14:29～17:01 的每一分钟。该均摊规则和分钟数据结构必须保留；当前需要解决的问题不是取消均摊，而是未选中的服务商停止采集，导致本可避免的采样间隔被人为拉长，最终出现一排高度几乎相同、参考价值较低的柱子。

本需求通过同时采集全部已配置 Provider 缩短采样间隔，使累计差额尽量落在更小的分钟范围内，同时明确保留长间隔情况下的现有均摊行为。

## 3. 需求目标

### 3.1 核心目标

1. 标题栏服务商下拉框只控制当前展示范围，不再决定后台唯一采集对象。
2. 应用运行期间，后台持续采集所有已配置凭据的服务商。
3. 各服务商独立保存采样快照、用量数据、刷新状态和错误状态。
4. 用户切换服务商时优先展示该服务商的最新缓存，不重新开始采样周期。
5. 保持现有估算分时结构：同一 Provider、同一自然日内，只要存在前后两次成功采样，就把累计差额平均补入两次采样之间的每一分钟，不因间隔过长而改变归属方式。
6. 通过后台同时采集所有已配置服务商，尽量缩短相邻采样间隔，提高现有估算分时的连续性和参考价值。

### 3.2 用户可感知结果

用户查看 Codex 时，后台仍持续采集 DeepSeek 和小米 MiMo：

```text
后台采集周期
├─ DeepSeek：凭据已配置 → 独立采集并更新 DeepSeek 快照
├─ 小米 MiMo：凭据已配置 → 独立采集并更新 MiMo 快照
└─ Codex：本地环境可用 → 独立采集并更新 Codex 快照

标题栏当前选择 Codex
└─ 界面只读取并展示 Codex 快照
```

切换回小米 MiMo 后，应立即显示后台已经持续采集的 MiMo 数据，不应因为此前查看了其他服务商而形成数小时采样空档。

## 4. 名词定义

| 名词 | 定义 |
| --- | --- |
| 当前展示服务商 | 标题栏下拉框当前选中的 Provider，仅决定界面读取哪个 Provider 的快照 |
| 已配置服务商 | `Provider.is_configured()` 返回 `True` 的 Provider，表示采集所需配置项已具备 |
| 凭据有效 | 最近一次实际请求通过鉴权；仅凭本地存在 Cookie、Token 或路径不能提前证明远端仍接受该凭据 |
| 成功采样 | 成功获得可用于累计差额计算的当日用量数据，并写入该 Provider 的采样快照 |
| 估算分时 | 根据相邻累计快照差额推算的数据，不是服务商返回的原始分钟明细 |
| 采样间隔 | 同一 Provider、同一自然日内相邻两次成功采样时间之间的分钟范围 |

## 5. 功能需求

### FR-01 展示范围与采集范围解耦

1. 保留现有 `ACTIVE_PROVIDER` 配置，继续表示“当前展示服务商”。
2. `ACTIVE_PROVIDER` 不再用于限制后台采集范围。
3. 标题栏下拉框切换后：
   - 立即读取目标 Provider 的最新本地缓存；
   - 不清空其他 Provider 的缓存；
   - 不停止其他 Provider 的后台采集；
   - 不重置目标 Provider 已建立的分钟采样基线。
4. 不改变现有下拉框选项顺序、服务商名称和用户操作方式。

### FR-02 后台采集对象

每个后台采集周期均检查 Provider 注册表：

1. 遍历全部已注册 Provider。
2. 仅为 `is_configured()` 返回 `True` 的 Provider创建采集任务。
3. 未配置 Provider 不发起网络请求、不产生鉴权错误通知。
4. Provider 配置在运行期间新增、删除或修改后，下一个采集周期自动重新计算采集对象。
5. 不新增需要用户重复维护的服务商启用列表；是否进入采集集合以 Provider 自身的 `is_configured()` 结果为准。

说明：

- “已配置”不等于“凭据一定有效”。凭据有效性必须以实际采集结果为准。
- Codex 的配置有效性继续按现有本地环境检测规则判断。

### FR-03 独立并发采集

1. 每个 Provider 使用独立后台任务采集，不能因一个 Provider 响应缓慢而阻塞其他 Provider。
2. 同一个 Provider 同一时间最多只能存在一个采集任务。
3. 某 Provider 上一轮任务尚未结束时，本轮跳过该 Provider，不重复排队。
4. 不同 Provider 可以并行执行。
5. 每个 Provider 使用独立的请求配置快照和 HTTP 会话，任务结束后按现有约定关闭 Provider 资源。
6. 应用退出时停止接收新任务，并按现有关闭流程清理等待中的后台任务。

### FR-04 采集频率

1. 当前展示服务商继续遵循现有 `REFRESH_INTERVAL`。
2. 非当前展示服务商默认每 60 秒采集一次。
3. 为避免高频请求，当 `REFRESH_INTERVAL` 小于 60 秒时，非当前展示服务商仍不得快于 60 秒采集一次。
4. 当 `REFRESH_INTERVAL` 大于 60 秒时，本期仍以 60 秒作为后台分时采样周期，确保服务商切换不会制造长采样空档。
5. 后台采集不得触发历史月份的重复全量同步：
   - 小米 MiMo 非当前展示时使用现有轻量采集路径；
   - 其他 Provider 应优先复用当前月份/当前日采集结果和本地历史缓存；
   - 历史补同步继续遵循现有批次和缓存规则。

### FR-05 Provider 级快照与状态隔离

每个 Provider 独立维护：

- 最新成功数据快照；
- 最近尝试时间；
- 最近成功时间；
- 是否正在刷新；
- 是否存在待执行刷新；
- 最近错误；
- 分时累计基线；
- 分时明细。

隔离规则：

1. MiMo 采集失败不能把当前 Codex 界面变为错误状态。
2. DeepSeek 采集超时不能阻止 MiMo 快照更新。
3. 非当前 Provider 完成采集后只更新自己的缓存，不得覆盖当前界面的 `_data`。
4. 当前 Provider 完成采集后才刷新面板和悬浮球展示。
5. Provider 切换后，旧 Provider 的晚到结果仍可写入旧 Provider 缓存，但不得覆盖新 Provider 的界面。

### FR-06 分时差额归属规则

小米 MiMo、DeepSeek 等只返回按日累计用量、未返回原始调用时间戳的 Provider，继续使用估算分时，但必须遵循以下规则。

#### 6.1 首次采样

- 仅建立当日累计基线。
- 不把首次看到的累计值写入某一分钟。
- 界面提示“已建立估算基线，下一次成功采样后显示分时数据”。

#### 6.2 同一自然日内的后续成功采样

同一 Provider、同一自然日内，只要已有前一次成功采样：

1. 计算三类 Token 累计差额及费用差额。
2. 差额为零时不生成分钟记录。
3. 正差额按现有估算规则平均分配到前一次成功采样之后、截至本次成功采样所在分钟的全部分钟点。
4. 图表必须始终标注“估算”，说明其不是平台原始分钟明细。

采样间隔长度不改变上述规则。例如两次成功采样相隔 153 分钟，正差额仍平均补入中间 153 个分钟点，以保持现有分时数据结构和图表连续性。

#### 6.3 采样中断后恢复

以下情况可能导致两次成功采样间隔变长：

- 应用退出后在同一自然日重新启动；
- 电脑休眠后在同一自然日恢复；
- 网络中断后恢复；
- Provider 鉴权失败后恢复；
- 用户此前选择其他 Provider，旧版本未对当前 Provider 持续采样。

处理规则：

1. 如果前后快照属于同一 Provider、同一自然日，继续计算累计差额并平均补入中间每一分钟。
2. 不因间隔过长而丢弃差额、重置当日基线或改用新的分时数据结构。
3. 本需求通过同时采集所有已配置 Provider，降低由用户切换服务商造成长间隔的概率。
4. 如果前一次采样时间晚于本次采样时间，或两次采样跨越 Provider 自然日，继续沿用现有跨日/时间异常处理：仅重建基线，不生成跨日分钟记录。

#### 6.4 平台累计值回退

任一累计字段出现负差额时：

1. 视为平台修正、账单重算或账号范围变化。
2. 不写入负分钟用量。
3. 使用本次累计值重建基线。
4. 保留现有“平台已校正当前数据”状态提示。

### FR-07 保持现有分时存储结构

1. 继续使用现有 `minute_usage`、`minute_usage_snapshot`、`minute_cost_usage` 和 `minute_cost_snapshot` 数据结构。
2. 不新增“未定位用量”表、字段或独立统计口径。
3. 不修改现有分钟主键、Token 分类、费用结构、读取接口和保存天数。
4. 同一次采样结果必须幂等，重复回调不能重复累计。
5. 数据按 Provider 隔离。
6. 清理失败不能影响正常账单采集。
7. 多 Provider 同时采集不得破坏已有 `usage.db`，不得丢失日账单和现有分钟数据。

### FR-08 分时界面

1. 分时视图始终显示“估算”标识，不得根据窗口宽度隐藏。
2. 保持现有“命中缓存”“未命中”“输出”三类堆叠结构、时间轴、导航条、日期切换和峰值摘要。
3. 长采样间隔产生的均摊分钟数据与短采样间隔数据使用相同图表结构，不增加灰色中断区域或其他特殊结构。
4. 用户切换日期时继续按现有规则切换该日分钟数据。
5. 日使用金额、日 Token、本月累计、近 7 天和历史总计继续使用现有日账单口径。

### FR-09 凭据失效与恢复

1. 后台 Provider 鉴权失败时，仅更新该 Provider 的错误状态。
2. 同一 Provider 的相同鉴权错误只通知一次，成功恢复后才允许再次通知。
3. 非当前 Provider 鉴权失败不得自动切换当前展示服务商。
4. 非当前 MiMo 的后台续期不得意外弹出可见浏览器窗口；需要用户交互时通过通知引导用户切换到 MiMo 或打开设置处理。
5. 凭据恢复后的第一次成功采样，如果与前一次快照属于同一自然日，继续按累计差额均摊到中间每一分钟；跨自然日时沿用现有基线重建规则。

### FR-10 手动刷新与切换行为

1. 点击“刷新”只强制刷新当前展示服务商，避免一次用户操作同时高频请求所有平台。
2. 后台定时采集继续按各 Provider 周期运行。
3. 切换到已有成功缓存的 Provider 时立即展示缓存，并在需要时异步刷新该 Provider。
4. 切换到尚无缓存的 Provider 时显示加载状态，但不影响其他 Provider 后台任务。
5. 快速连续切换时，任何旧 Provider 的完成回调不得覆盖最新选择。

## 6. 非功能需求

### NFR-01 性能与请求控制

- 不得在 UI 线程执行网络采集。
- 同一 Provider 禁止并发重复请求。
- 后台非当前 Provider 的最短采集周期为 60 秒。
- 历史账单补同步不得随每分钟后台采集重复执行。
- 单个 Provider 超时不延长其他 Provider 的采样间隔。

### NFR-02 数据安全

- 日志不得输出 Cookie、Token、API Key、完整请求头或浏览器会话值。
- Provider 错误日志只记录 Provider ID、错误码、数据源和必要的非敏感上下文。
- 不因后台采集而新增凭据明文持久化方式。

### NFR-03 兼容性

- 保持 `ACTIVE_PROVIDER` 现有含义对外兼容，但内部仅作为展示范围使用。
- 保持标题栏下拉框操作、Provider 名称和现有卡片返回结构不变。
- 保持 `daily_usage`、余额、本月累计、近 7 天和历史统计口径不变。
- 保持已有 Provider 接口和具体 Provider 实现可复用，不要求为本需求重写 Provider。
- 新增 Provider 只要注册并正确实现 `is_configured()`，即可自动进入后台采集集合。

### NFR-04 可观测性

建议增加不含敏感信息的调试日志：

```text
Provider collection started: provider=mimo reason=periodic
Provider collection skipped: provider=mimo reason=in_flight
Provider collection completed: provider=mimo status=ok elapsed_ms=860
Minute delta distributed: provider=mimo gap_minutes=153 token_total=826741
```

正常每分钟成功采集日志应控制级别或频率，避免日志膨胀。

## 7. 业务规则示例

### 示例 A：当前查看 Codex，MiMo 没有使用

```text
16:58 MiMo 后台累计 100万
16:59 MiMo 后台累计 100万
17:00 MiMo 后台累计 100万
17:01 MiMo 后台累计 100万
```

结果：

- MiMo 分时增量为 0；
- 不生成任何 MiMo 柱子；
- 17:01 切回 MiMo 时直接显示后台持续采集形成的现有分时结果。

### 示例 B：当前查看 Codex，16:20 附近使用了 MiMo

```text
16:19 MiMo 后台累计 100万
16:20 MiMo 后台累计 100.5万
16:21 MiMo 后台累计 100.5万
```

结果：

- 约 0.5 万 Token 进入 16:20 附近的估算分钟桶；
- 其他分钟保持为 0；
- 图表明确标注为估算。

### 示例 C：应用休眠 153 分钟

```text
14:28 MiMo 累计值 A
14:29～17:00 无成功采样
17:01 MiMo 累计值 B
B - A = 82.67万
```

结果：

- 继续向 14:29～17:01 创建 153 个分钟点；
- 82.67 万按照现有算法平均分配到这 153 个分钟点；
- 三类 Token 和费用分别保持原有分时结构；
- 分时 Token、费用分类合计必须分别等于两次累计快照的正差额。

### 示例 D：MiMo 鉴权失败后恢复

```text
10:00 最后一次成功采样
10:01 开始鉴权失败
10:20 凭据恢复并成功采样
```

结果：

- 如果 10:00 和 10:20 属于同一自然日，恢复时的正差额继续平均分配到 10:01～10:20；
- 10:20 的累计值同时成为后续采样的新基线；
- 如果恢复时已经跨越自然日，则沿用现有跨日基线重建规则。

## 8. 数据迁移与历史数据

1. 本需求不改变已有分钟数据结构和长区间均摊规则。
2. 已存在的分钟数据不得删除、覆盖、迁移或重新归类。
3. 不新增数据库迁移脚本，不新增“未定位用量”表。
4. 多 Provider 调度改造必须继续复用现有 Provider 维度的分钟表主键和快照结构。
5. 如实现过程中发现必须修改数据库结构，应停止开发并重新评审，不得在本需求中擅自扩展。

## 9. 影响范围

预期需要检查并最小修改以下模块：

| 模块 | 影响 |
| --- | --- |
| `api/providers/__init__.py` | 保留单 Provider 获取能力，新增或复用全部已配置 Provider 的枚举逻辑 |
| `data/store.py` | Provider 独立采集入口、独立快照及现有分时估算链路复用 |
| `data/history.py` | 原则上不改变数据结构；仅检查多 Provider 并发写入和现有幂等行为 |
| `ui/qt_widget.py` | 多 Provider 调度、Provider 级 in-flight 状态、完成回调隔离和手动刷新 |
| `ui/qt_panel.py` | 保持现有分时图结构；仅确保多 Provider 快照切换正确 |
| `ui/qt_settings.py` | 如需要说明后台采集频率，仅增加必要提示，不新增复杂配置 |
| `config/defaults.py` | 仅在最终确认需要独立后台周期配置时新增字段 |
| `tests/test_store.py` | 多 Provider 缓存、差额归属、错误隔离测试 |
| `tests/test_history.py` | 长短采样间隔均摊、幂等和 Provider 隔离回归测试 |
| `tests/test_refresh.py` | 并发调度、重复任务拦截、切换和晚到结果测试 |
| `tests/test_qt_ui.py` | Provider 切换后现有分时结构和摘要保持不变 |

不应修改：

- 现有服务商账单接口协议；
- 标题栏下拉框的用户操作协议；
- 日账单、余额、本月累计和近 7 天统计口径；
- 与本需求无关的主题、布局、更新器和凭据存储逻辑。

## 10. 验收标准

### AC-01 多服务商持续采集

前置条件：DeepSeek、MiMo、Codex 均已正确配置，当前展示 Codex。

验收：

- 连续运行 5 分钟后，三个 Provider 均至少有独立采集尝试；
- MiMo 和 DeepSeek 的最近成功时间持续更新；
- 切换到 MiMo 后立即显示其最新缓存；
- 切换行为不重新建立或丢失 MiMo 已有基线。

### AC-02 未使用的 Provider 不生成分时数据

前置条件：当前展示并使用 Codex，MiMo 后台采集成功但累计值不变。

验收：

- MiMo 不生成分钟柱子；
- 切换到 MiMo 后显示“今日暂无 Token 消耗”或当天已有的真实估算结果。

### AC-03 连续采样增量

前置条件：MiMo 相邻成功采样间隔约 60 秒，累计 Token 增加。

验收：

- 差额只进入相邻采样区间；
- 不扩散到更早时间；
- Token 分类合计等于累计差额；
- 图表显示“估算”。

### AC-04 长间隔继续均摊

前置条件：MiMo 两次成功采样间隔 153 分钟，累计增加 82.67 万。

验收：

- 创建 14:29～17:01 共 153 个分钟点；
- 82.67 万按现有算法平均补入这 153 个分钟点；
- 不新增“未定位用量”或其他分时结构；
- Token、费用及三类 Token 分类的分钟合计分别等于两次累计快照的正差额；
- 日 Token 总量保持不变；
- 图表继续使用现有堆叠柱状图、时间轴、导航条和峰值摘要。

### AC-05 错误隔离

前置条件：MiMo 鉴权失效，当前展示 Codex。

验收：

- Codex 正常刷新和展示；
- MiMo 错误仅写入 MiMo 状态；
- 界面不自动切换到 MiMo；
- 不重复弹出相同错误通知；
- 不弹出非用户触发的可见续期浏览器。

### AC-06 重复任务控制

前置条件：某 Provider 请求耗时超过一个采集周期。

验收：

- 该 Provider 不出现第二个并发任务；
- 其他 Provider 仍正常采集；
- 任务完成后下一周期可继续采集。

### AC-07 快速切换

前置条件：依次快速选择 DeepSeek、MiMo、Codex。

验收：

- 最终界面只显示 Codex；
- DeepSeek 或 MiMo 的晚到结果不能覆盖 Codex 界面；
- 三个 Provider 的成功结果仍分别进入各自缓存。

### AC-08 数据库兼容

前置条件：使用包含既有日账单和分钟数据的旧版 `usage.db` 启动新版。

验收：

- 本需求不触发分钟数据库结构升级；
- 既有日账单和分钟数据未丢失；
- 新旧版本的 `minute_usage`、`minute_usage_snapshot`、`minute_cost_usage` 和 `minute_cost_snapshot` 结构保持一致；
- 多 Provider 同时写入时仍按 Provider 正确隔离。

## 11. 测试要求

至少覆盖以下测试：

1. 全部已配置 Provider 被纳入后台采集集合。
2. 未配置 Provider 不创建任务。
3. Provider 级 in-flight 防重。
4. 多 Provider 任务可以独立完成。
5. 非当前 Provider 结果只更新自身缓存。
6. 当前 Provider 结果更新界面。
7. Provider 快速切换时旧结果不覆盖新界面。
8. 首次采样只建立基线。
9. 短间隔正差额正常均摊。
10. 长间隔正差额继续平均补入全部中间分钟。
11. 同一自然日内应用重启、休眠、断网或鉴权恢复后继续按累计差额均摊。
12. 零差额不生成记录。
13. 跨日差额不生成跨日分钟记录。
14. 累计值回退只重建基线。
15. 同一次采样重复保存保持幂等。
16. 多 Provider 分钟记录按 Provider 隔离。
17. 一个 Provider 的网络、存储或鉴权错误不影响其他 Provider。
18. 非当前 MiMo 鉴权失效不打开可见浏览器。
19. Provider 切换后现有分时图结构和摘要保持不变。
20. `git diff --check` 无空白错误。

## 12. 已知限制

1. MiMo 当前接口只提供按日、按模型累计值，没有原始调用时间戳。
2. 即使每分钟持续采集，分钟数据仍然是相邻累计快照差额的估算结果。
3. 如果服务商自身延迟发布账单，程序只能知道“本次观察到累计值变化”，无法证明真实调用发生在本分钟。
4. 在服务商提供带时间戳的原始用量明细前，不得把估算分时描述为精确调用时间。
5. 同时采集可以显著减少“因为用户切换服务商而停止采样”造成的长间隔，但不能消除服务商账单延迟、应用退出、休眠或断网等情况。
6. 当间隔较长时，仍按现有规则把累计差额平均补入中间每一分钟；这是产品明确保留的估算口径，不代表平台提供了真实分钟调用时间。

## 13. 待评审决策

1. 是否固定非当前 Provider 后台采集周期为 60 秒，还是在设置中允许配置 60～600 秒。
2. 后台 Provider 鉴权失败是否需要托盘通知，或仅在用户切换到该 Provider 时提示。

在以上决策确认前，推荐默认值为：后台周期固定 60 秒、保留现有分时数据结构和长间隔均摊规则、鉴权失败按 Provider 去重后发送一次托盘通知。
